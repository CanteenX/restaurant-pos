# Design: accounting day book and approval gaps (#384)

Status: discovery proposal, awaiting independent design review. This proposes a reporting view rather than replacing existing accounting or importing upstream code.

## Existing behaviour and actual gap

Expenses already support branch-scoped pending queues and approve/reject routes (`apps/backend/src/modules/accounting/accounting.controller.ts:51`, `:70`, `:81`, `:101`); approval uses `expenses.approve`, and the service prevents the recorder deciding their own expense (`accounting.service.ts:93`). Threshold rules exist in `expense-approval.ts`; petty-cash payouts and float management already exist in `petty-cash.service.ts`, with transaction-bound audit for payouts. Audit listing exists behind `audit_log.view` (`apps/backend/src/audit/audit.controller.ts:13`). Cash-closing calculations exist in `accounting.calc.ts`. The candidate gap is a single chronological, reconciled day-book view across eligible financial sources, with clear drill-through and permission boundaries. It is not evidence that approvals, petty cash, or an audit log are missing.

## Data and behaviour

The first version is a read-only, branch-scoped projection, not a new journal. Use integer paise or exact Decimal arithmetic throughout; never round floats. The source/status/tender matrix is explicit:

| Source | Inclusion and date | Signed contribution and reconciliation |
|---|---|---|
| Payment | Persisted Payment on a non-voided order; `createdAt` in branch timezone. Include partial payments and all PaymentMethod values separately. Gateway attempts are excluded: count only their resulting Payment. | Positive `amount` (net of change), never `tendered`; mixed tenders are individual rows, not an additional order total. |
| Refund | Persisted Refund on the authorised order; `createdAt` in branch timezone, including partial refunds. | Negative `amount`, grouped by its recorded method; stock returns are not monetary rows. |
| Expense | APPROVED only, including legacy APPROVED; use `spentOn` business date. PENDING/REJECTED are excluded, even if created that day. | Negative `amount`; indicate till versus petty-cash source. An expense linked to a petty-cash PAYOUT is the expense row, not a second expense amount. |
| Petty cash | TOP_UP and ADJUST only, by `businessDate`; show PAYOUT as a linked, non-additive reference when its approved expense is visible. | Signed float movement; a till-funded TOP_UP is an internal transfer, not income or expense. ADJUST is a separately labelled float adjustment, not sales. Never combine the float ledger with expense totals as external cash flow. |
| CashClosing | By `businessDate`, as a separate reconciliation summary only. | Opening, expected, counted and variance are non-additive snapshots; never add cashSales, cashExpenses or top-ups to transaction totals. |

Do not infer void or cancellation from a missing status: verify the actual order states and add explicit fixtures before implementing; ambiguous historical rows are excluded and counted as a data-quality warning, not silently reclassified. Use BranchTimeService for instants and existing DATE fields as recorded business dates; v1 business days start at local midnight, with a half-open `[start, next-day)` interval. Return source type and stable source ID, and link only to an independently authorised detail endpoint. Audit events remain separate. Permission-limited responses omit both the source and its totals, label results incomplete, and never reveal hidden counts or amounts.

## Permissions and migration

Introduce independently grantable `accounting.daybook.view` as a permission record and additive seed/backfill, with no automatic expansion of existing custom roles; preserve the locked Admin invariant and grant ceilings. Require `reports.access` and that key for the endpoint. Payment/refund rows additionally require `dashboard.sales.view`; approved expenses require `accounting.manage`; petty-cash rows require `petty_cash.manage`; closing summaries require `accounting.manage`. Each is evaluated with live DENY semantics, including implied permissions; exports additionally require `data.export` and the identical source filters. `expenses.approve` and `audit_log.view` alone confer no financial-source visibility. Detail links enforce their own existing route permissions. No role-name checks.

The current BranchAccessService checks restaurant ownership, not staff assignments. This feature fails closed unless a UserBranch assignment exists for the selected branch and the branch belongs to the session restaurant; this includes owner/admin users, so provisioning must explicitly assign them before rollout rather than silently widening access. Test same-restaurant unassigned branches, cross-restaurant IDs, missing assignments and grant expiry. Validate request boundaries with Zod and use parameterised queries. Initial projection changes no financial data; any permission seed or index migration must be additive, backed up first, upgrade existing populated installs safely, and supply a tested rollback. Never rewrite historical expenses or audit rows.

## Tests and open design questions

Limit a request to 31 inclusive local business days, 100 rows per page, a 1 MiB response and 5-second database statement timeout; reject oversized requests, do not truncate totals silently. Aggregate and page must share one read-only repeatable-read snapshot, with a bounded source-row budget; if the budget is exceeded return a clear narrowing-required error. Bind a signed opaque cursor to restaurant, branch, date range, granted-source set and a stable `(businessDate, eventTime, sourceType, sourceId)` ordering. Cursors do not promise a cross-request frozen snapshot: return an `asOf` timestamp, and reject changed filters/permissions; changes between pages require an explicit refresh and may affect later pages. Use the same bounded snapshot and filters for export; do not build unbounded in-memory `findMany` lists.

Unit tests cover every matrix status and tender, mixed payments, partial refunds, voids, petty-cash payouts/top-ups, non-double-counted cash closings, signed adjustments, paise and timezone boundaries. PostgreSQL/API tests cover denied and expired grants, hidden totals and counts, cross-restaurant and same-restaurant unassigned branches, owner/admin assignment provisioning, stable tie-breaking, changed cursor filters, source/detail/export fences, aggregate/page consistency during concurrent writes and budget timeout. Browser tests cover permission-limited results, accessible date controls and permitted detail navigation. Review the unresolved legacy-order void mapping and the feasibility of a bounded repeatable-read query before implementation; do not silently loosen these safeguards. No new approval workflow is proposed.
