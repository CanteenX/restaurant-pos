# Design: accounting day book and approval gaps (#384)

Status: discovery proposal, awaiting independent design review. This proposes a reporting view rather than replacing existing accounting or importing upstream code.

## Existing behaviour and actual gap

Expenses already support branch-scoped pending queues and approve/reject routes (`apps/backend/src/modules/accounting/accounting.controller.ts:51`, `:70`, `:81`, `:101`); approval uses `expenses.approve`, and the service prevents the recorder deciding their own expense (`accounting.service.ts:93`). Threshold rules exist in `expense-approval.ts`; petty-cash payouts and float management already exist in `petty-cash.service.ts`, with transaction-bound audit for payouts. Audit listing exists behind `audit_log.view` (`apps/backend/src/audit/audit.controller.ts:13`). Cash-closing calculations exist in `accounting.calc.ts`. The candidate gap is a single chronological, reconciled day-book view across eligible financial sources, with clear drill-through and permission boundaries. It is not evidence that approvals, petty cash, or an audit log are missing.

## Data and behaviour

The first version is a read-only, branch-scoped projection, not a new journal. Use integer paise or exact Decimal arithmetic throughout; never round floats. The source/status/tender matrix is explicit:

| Source | Inclusion and date | Signed contribution and reconciliation |
|---|---|---|
| Payment | Persisted Payment joined to its Order and Branch, with both branch and restaurant filters, `createdAt` in branch timezone. Include OPEN, BILLED, PAID and CANCELLED orders; partial payments remain recorded. Mark CANCELLED-with-payment as an anomaly: normal cancellation rejects orders with payments, but historical/racing data must not vanish. Gateway attempts are excluded: count only their resulting Payment. | Positive `amount` (net of change), never `tendered`; mixed tenders are individual rows, not an additional order total. CASH is drawer cash; CARD, UPI, WALLET, BANK_TRANSFER and OTHER are separate external tender buckets; GIFT_CARD and STORE_CREDIT are separate liability-redemption buckets, never additional cash or external receipts. |
| Refund | Persisted Refund joined through Order and Branch with both branch and restaurant filters, regardless of current OPEN/BILLED/PAID/CANCELLED status; `createdAt` in branch timezone, including partial refunds. CANCELLED-with-refund is flagged as anomalous, not hidden. | Negative `amount`, grouped by its recorded method, with CASH, other external methods and GIFT_CARD/STORE_CREDIT kept in the corresponding separate buckets; stock returns are not monetary rows. |
| Expense | APPROVED only, including legacy APPROVED; use `spentOn` business date. PENDING/REJECTED are excluded, even if created that day. | Negative `amount`; indicate till versus petty-cash source. An expense linked to a petty-cash PAYOUT is the expense row, not a second expense amount. |
| Petty cash | TOP_UP and ADJUST only, by `businessDate`; show PAYOUT as a linked, non-additive reference when its approved expense is visible. | Signed float movement; a till-funded TOP_UP is an internal transfer, not income or expense. ADJUST is a separately labelled float adjustment, not sales. Never combine the float ledger with expense totals as external cash flow. |
| CashClosing | By `businessDate`, as a separate reconciliation summary only. | Opening, expected, counted and variance are non-additive snapshots; never add cashSales, cashExpenses or top-ups to transaction totals. |

OrderStatus has only OPEN, BILLED, PAID and CANCELLED; it has no void state. Finished orders may be permanently deleted and Payment/Refund cascade with them. Therefore this projection cannot reconstruct a complete historical ledger: display a constant generic "historical records may be missing" limitation to every viewer, and never infer or reconstruct financial rows from audit snapshots. It must not claim accounting completeness or leak deleted/hidden counts. Payment rows on legacy cancelled orders are included and flagged only to authorised sales viewers. Use BranchTimeService for instants and existing DATE fields as recorded business dates; v1 business days start at local midnight, with a half-open `[start, next-day)` interval. Return source type and stable source ID, and link only to an independently authorised detail endpoint. Audit events remain separate. Permission-limited responses omit both the source and its totals, label results incomplete, and never reveal hidden counts or amounts.

## Permissions and migration

Introduce independently grantable `accounting.daybook.view` as a permission record and additive seed/backfill, with no automatic expansion of existing custom roles; preserve the locked Admin invariant and grant ceilings. Require `reports.access` and that key for the endpoint. Payment/refund rows additionally require `dashboard.sales.view`; approved expenses require `accounting.manage`; petty-cash rows require `petty_cash.manage`; closing summaries require `accounting.manage`. Each is evaluated with live DENY semantics, including implied permissions; exports additionally require `data.export` and the identical source filters. `expenses.approve` and `audit_log.view` alone confer no financial-source visibility. Detail links enforce their own existing route permissions. No role-name checks.

The current BranchAccessService checks restaurant ownership, not staff assignments. This feature fails closed unless a UserBranch assignment exists for the selected branch and the branch belongs to the session restaurant; this includes owner/admin users, so provisioning must explicitly assign them before rollout rather than silently widening access. Test same-restaurant unassigned branches, cross-restaurant IDs, missing assignments and grant expiry. Validate request boundaries with Zod and use parameterised queries. Initial projection changes no financial data; any permission seed or index migration must be additive, backed up first, upgrade existing populated installs safely, and supply a tested rollback. Never rewrite historical expenses or audit rows.

## Tests and open design questions

Limit a request to 31 inclusive local business days, 100 visible rows total, a 1 MiB response and a 5-second database statement timeout. In one read-only repeatable-read transaction, each permitted, branch-scoped source query uses deterministic indexed filters and `LIMIT 101`; combine the bounded results, and reject with a narrowing-required error if the combined count exceeds 100 or output exceeds the byte budget. Compute totals only from that same complete bounded result and never silently truncate. There is no cursor or multi-page snapshot in v1: users narrow dates to retrieve a complete result; this avoids missed or duplicated historical/backdated inserts between pages. Return `asOf` and make refresh a new snapshot. Exports use the same filters, limits and transaction strategy, with `data.export`; do not build unbounded `findMany` lists. Before adding pagination in a later design, require a durable materialised snapshot or equivalent fixed row set, an expiring signed cursor bound to restaurant, branch, filters and permission scope, plus tests for backdated inserts, updates, deletes, permission changes and multiple server instances.

Unit tests cover all four order statuses and tenders, mixed and partial payments, partial refunds, rejected cancellation with prior payments, legacy cancelled-with-payment anomalies, petty-cash payouts/top-ups, non-double-counted closings, signed adjustments, paise and timezone boundaries. PostgreSQL/API tests cover deletion/cascade and constant completeness warning, denied/expired grants, hidden totals/counts, cross-restaurant and same-restaurant unassigned branches, owner/admin assignment provisioning, source/detail/export fences, exact 100/101 boundaries, snapshot consistency under concurrent and backdated inserts, indexed plans and budget timeout. Browser tests cover permission-limited results, narrowing-required state, accessible date controls and permitted detail navigation. No new approval workflow is proposed.
