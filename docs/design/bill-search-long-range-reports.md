# Bill search and long-range reports (design, #382)

Status: proposed; independent design review required before implementation.

## Current state and goal

Reports require `reports.access`, enforce branch access, and currently reject ranges longer than 366 days (`apps/backend/src/modules/reports/reports.controller.ts`, `reports.service.ts`). Existing order list and detail routes require `orders.create` (`apps/backend/src/modules/orders/orders.controller.ts`), so granting report-only users those routes would broaden write-related authority. Add up to five years of branch-scoped historical reporting, useful date presets, and read-only bill search/detail for authorized report users without granting order creation or editing.

## Data and interface

Reuse existing `Order`, order lines, payment and branch relations. Define bill search and detail projections explicitly: bill number, business date/time, status, totals/tax and item lines; exclude personal identifiers, payment tokens and internal notes unless a separate existing permission and an explicit product decision allow them. MVP searches settled `PAID` bills by `billedAt`; open, cancelled and other statuses are excluded rather than silently using creation time. Missing `billedAt` is excluded and surfaced as a data-quality metric. Search by bounded bill number and date range, ordered by `(billedAt, id)` descending, with an opaque cursor containing both values and bound to the branch, filters and range. Use keyset predicates, maximum page size 100 and cancellation; never allow unrestricted cross-branch search. Unknown or unauthorized IDs return a non-disclosing 404.

Offer branch-local today, yesterday, week, month, year and custom presets. Resolve the restaurant timezone through `BranchTimeService.tzForBranch` (current fallback Asia/Kolkata), validate real calendar dates, and allow at most five calendar years inclusive: for start date D, end must be no later than D plus five calendar years minus one day, using calendar arithmetic across leap days. Convert inclusive local dates to a half-open instant range with DST-aware timezone handling; label the date as billed, not created. A new bounded bill search is limited to 100 rows and 1 MiB serialized output per page, with a 5-second query timeout; fail explicitly rather than truncate silently. Keep the existing 366-day cap on every report aggregation until it is individually converted to bounded database aggregation with measured five-year query plans, explicit row/output budgets and timeout tests. Preserve existing report semantics and `data.export` checks for exports.

## Permissions and migration

Propose a distinct `reports.bills.read` permission, stored and granted as data and enforced alongside `reports.access` and `dashboard.sales.view` for this financial projection; an explicit DENY on any required key wins over implication and grants. No role-name checks or automatic escalation: independently review seed/backfill policy before granting existing users access. `BranchAccessService` currently verifies only restaurant ownership, not staff assignments: for this new endpoint additionally require an explicit `UserBranch` assignment for the requested branch, fail closed if absent, and apply the same predicate to search and detail. Document the rollout and migration policy for staff with no assignments; do not silently grant restaurant-wide access. Keep all mutation endpoints behind existing permissions. Validate controller inputs with Zod, use parameterized Prisma queries, and project fields deliberately.

MVP can reuse existing order data; no data conversion is needed. Add only query indexes justified by measured plans, via a backward-compatible migration after backup and with a rollback plan. Permission-key rollout must drain old instances before new keys are granted. Existing installations retain their current grants until an explicitly reviewed migration assigns new access.

## Verification and risks

Unit tests cover presets, billedAt/PAID semantics, calendar boundaries, reversed ranges, leap days, the exact five-year boundary and timeout/output-budget handling. API/database tests seed two restaurants and multiple same-restaurant branches with differing assignments; verify every required permission and live DENY independently, no-assignment fail-closed behavior, mutation denial, cross-tenant 404, field redaction and stable cursors with identical timestamps. Test that unconverted reports still reject ranges above 366 days and exports require `data.export`. Performance tests exercise five years of synthetic data and query plans; Playwright verifies presets, bill search/detail, empty/error states, accessibility and no order-edit controls. Test retention and each report's budgets before widening it.
