# Design: production stock journal (#383)

Status: discovery proposal, awaiting an independent security-focused design review and owner decisions below. No upstream code or migration is included. Suggested policies are alternatives, not approved product decisions.

## Existing behaviour and gap

Nventra already stores recipe lines and calculates recipe cost (`apps/backend/src/modules/inventory/inventory.service.ts:213`), deducts recipe or direct ingredients at checkout (`inventory.service.ts:353`; `apps/backend/src/modules/orders/orders.service.ts:1755`), and records receipts, consumption, adjustments, waste and reversals in branch-scoped `StockMovement` (`apps/backend/prisma/schema.prisma:1208`). The inventory API exposes ingredient movement history and waste (`inventory.controller.ts:171`, `:440`), and the web app has recipe/stock-tracking controls. This is not a greenfield recipe feature. The candidate gap is a first-class production voucher: recording a batch of prepared stock produced from inputs, its yield and actual cost, before subsequent consumption or sale. Upstream's stock-journal idea motivates discovery; its schema is not assumed compatible.

## Proposed model and workflow

After the decisions below, propose branch-scoped `ProductionVoucher` (id, restaurant/branch, status, request fingerprint, idempotency key, creator, timestamps and reversal reference) and immutable input/output lines (ingredient/batch, signed base-unit quantity and exact cost snapshot). Link existing `StockMovement` entries to the voucher; the existing ledger remains the balance authority. Drafts move no stock. For the prepared-output alternative, create a normal `Ingredient` and an output `StockBatch`, explicitly map a menu item to it using a reviewed prepared/direct tracking mode, and consume the prepared batch at sale rather than deducting the input recipe twice. Do not silently reinterpret historical `RECIPE` sales. Returns must reverse the original sale's recorded movements and lot costs, not consult the item's current mode or today's recipe. This mapping requires owner approval and an audit of current sale/refund movement and report semantics before coding.

All writers touching the same stock, including checkout, return, receipts, waste, adjustments, purchase returns and voucher post/reversal, must participate in one reviewed transaction protocol: discover and lock branch/ingredient and affected batches in a globally consistent order **before** availability/cost reads, calculate from that transaction's fresh rows, then write balances, ledger, voucher and audit atomically. Establish a consistent order with order-row locks; bound deadlocks/serialization retries and retry the entire transaction with the same idempotency key. A voucher-only lock is insufficient. Drain old application writers before enabling the feature in a mixed-version deployment, then verify all writers use the protocol; old writers cannot safely coexist merely because the migration is additive.

Posting validates positive yield, units, quantities, cost precision and available input lots; writes signed input consumption and an output receipt in one transaction. Bind a unique branch/idempotency key to a canonical payload fingerprint: exact retries return the original result and conflicting payloads fail. Posted vouchers are immutable. Reversal is a separately idempotent compensating operation referencing the original voucher and its original input/output lots, quantities and costs, with an atomic audit event. Never erase movements, change original lot costs, reprice historical sales, or silently create stock when output has already been used. Reject reversal if original output is consumed unless an explicitly approved compensating workflow can account for every downstream movement; concurrent sale, receipt or reversal must not evade that check.

Use decimal arithmetic end-to-end, not binary floating-point: the existing ledger quantity is `Decimal(12,3)` and receipt unit cost is `Decimal(14,6)`; validate unit conversions and overflow before writes and reconcile rounding residuals explicitly. Input lot valuation must use the actual consumed batches and immutable unit-cost snapshots; an intervening receipt must not retroactively revalue them. Existing behavior and reporting around negative stock need a deliberate policy: do not silently assign guessed or negative-balance costs. Decide how to value output yield and loss, where monetary rounding occurs, and how negative inventory is reconciled before implementation.

### Owner decisions required before implementation

1. Prepared output: recommend a separately identified prepared `Ingredient`/batch mapped explicitly to a menu item; alternative is a distinct finished-goods entity. Confirm units, conversion, sale and historical-return expectations.
2. Yield/cost: recommend recording actual yield and input-lot costs with explicit waste/residual rounding; alternatives include planned yield or standard cost. Confirm rounding and food-cost treatment.
3. Shortage: recommend rejecting a post when inputs are insufficient, including existing negative balances; alternative is an explicitly costed negative-stock policy. Confirm expected operations during shortages.
4. Reversal after output consumption: recommend refusal until downstream movements are reconciled; alternative is a governed compensating adjustment with audit. Confirm the desired workflow and authority.

## Permissions and migration

Use permission checks rather than role-name checks. Reuse `inventory.manage` for the first design or add separately grantable `inventory.production.read` and `inventory.production.post` keys after review; roles remain data, Admin remains locked, and grant ceilings and live DENY overrides apply. Every request validates Zod input and effective permissions. Existing branch-access checks must not be assumed to enforce user branch assignments: specify and test the intended restaurant and assigned-branch policy, including owner/admin users lacking an assignment, before introducing endpoints. Add branch-scoped composite uniqueness/foreign-key fences or equivalent database-enforced references for voucher, line, ingredient, batch and movement links; test forged cross-restaurant and same-restaurant cross-branch IDs under concurrency. Validate existing data before adding constraints.

Add new tables, nullable links and indexes in additive migrations; historical movement, recipe and sale records remain unchanged, with no invented backfill. Back up and validate restore before migration. Test populated upgrades and rollback only while no new voucher data depends on the new schema; after writes, use a documented recovery/forward-fix plan rather than a destructive down migration. Test the mixed-version drain barrier and verify existing stock movement, sales and reporting consumers continue to interpret quantities, lot references, sales and returns correctly.

## Tests and review decisions

Unit tests cover decimal precision/overflow, unit conversion, yield, residual allocation, shortages and valuation after intervening receipts or negative balances. Deterministic PostgreSQL barrier tests interleave post with checkout, waste, receipt, adjustment and reversal, exercise ordered multi-ingredient locks, rollback/retry, conflicting keys, consumed-output reversal and original-lot/cost preservation. API tests cover effective permissions, live DENY, tenant and assigned-branch fences; browser tests cover draft/post/reversal and permission-limited views. Compare pre/post-upgrade sales, returns, movement history and reports with historical fixtures. Independently security-review the complete shared-writer protocol, owner decisions, data model and mixed-version rollout before implementation.
