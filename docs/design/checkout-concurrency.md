# Checkout and bill mutation concurrency (#391)

Status: design for security review; no implementation approved. Applies to the current Nventra schema and existing API contracts, not a direct upstream port.

## Problem and invariants

`orders.service.ts` reads the order, payments and calculated bill before the checkout transaction. A partial payment leaves the order OPEN. `addItems`, item edits, header edits, cancellation and merge also check state before their write transactions. Concurrent requests can therefore act on stale payments or items. The existing final OPEN-to-PAID conditional update and transactional inventory deduction protect the losing full checkout, but do not serialize all partial payments and edits.

For each branch-scoped order, commit a serial history: no payment exceeds the freshly computed balance; after the first payment bill figures and items cannot change; paid/cancelled orders cannot be edited or paid again; duplicate request IDs do not debit or create side effects twice. A committed payment, stock movements, coupon, loyalty, gift-card and fiscal-ledger effects must agree. Rollback of a losing transaction leaves none of its side effects. Preserve the current policy for gateway settlement where money has already moved; never silently discard or duplicate it.

## Proposed transactional boundary

Use a parameterised PostgreSQL `SELECT ... FOR UPDATE` on the order row inside the Prisma interactive transaction, scoped by both order ID and the already-authorised branch ID. Return the existing not-found behavior for missing/cross-branch rows. Acquire before every read that decides a write, then reload order, items, payments, customer attachment, status and acceptance through that same transaction client. Recompute totals, locked figures, paid amount, balance, coupon eligibility, discount ceiling and loyalty inputs from the locked state. Pass the transaction client through bill and marketing helpers rather than reading stale data through the root Prisma client. Keep read-only previews advisory; checkout must independently recalculate under lock.

Make checkout, add/change/remove item, editable header/table changes, cancellation and merge participate in the same protocol. Inventory/KOT/online QR and gateway code can mutate or settle orders outside these entry points; trace every writer and ensure it calls the same transaction boundary or participates in a documented compatible lock. Do not ship a checkout-only lock while a concurrent writer can still bypass it. For merge, lock both branch-scoped order rows in deterministic ascending ID order, reload both and reject if either changed status or has payments. Define a consistent global order for order, table, customer, coupon, gift-card, stock and fiscal-ledger locks after auditing all existing paths; existing implicit database locks may make a naive order unsafe. Handle timeout/deadlock/serialization failures as a bounded retry or explicit conflict, with no automatic replay of irreversible external actions. No network, SMTP, printer or payment gateway call should run while a database transaction is held. Emit events only after commit.

Recheck `requestId` under the order lock and preserve the database uniqueness constraint. Same ID with the same request returns the committed outcome without side effects; define and test behavior when the same ID carries different payment inputs, including the existing P2002 fallback. Different IDs must each see the updated balance. Keep first-payment coupon redemption and loyalty debit atomic, avoid a second redemption on later parts, and preserve guarded cross-order customer/gift-card balances. Validate QR override against the current locked state and coordinate already-captured gateway money with its idempotent settlement path; review lock ordering with gateway/QR service before rollout.

### Mandatory writer inventory and lock contract

Before enabling the protocol, enumerate every order/payment/item/table writer with entry point, transaction, side effects and fence test. This includes normal order endpoints; KOT state and item writers (including their current inverse acquisition order); table close and sibling-order recount; standalone/offline `applyOfflinePrices`; cleanup/expiry jobs; integration reward writers; raw sync upserts; QR; gateway initiation, callback and reconciliation; stock, customer, referral, coupon and gift-card writers. A writer that cannot participate must be fenced off while the feature is enabled, including background jobs and callbacks. A source grep alone is not evidence that raw SQL, asynchronous jobs or integrations are covered.

The candidate global lock rank is: branch/table rows (sorted ID), all involved order rows (sorted ID), payment intent/request rows (sorted ID), customer/referral rows (sorted ID), coupon and gift-card rows (sorted by type and ID), ingredient/batch rows (sorted by branch, ingredient and batch ID), then fiscal sequence/ledger rows. Table close must lock the table before orders, lock the relevant sibling orders in ascending ID, then recount their current committed state inside the same transaction before closing. Each writer must acquire every needed lock in this order before reading values used for its decision; never obtain a lower-ranked lock after a higher-ranked lock. Trace and refactor existing KOT, stock, customer and referral paths that violate this rank before enabling. Preflight the complete resource set; if it changes, abort and restart rather than adding out-of-order locks. This rank is a proposal, not a proof: the implementation plan must inventory implicit foreign-key/unique/trigger locks and verify the full wait-for graph first. Use a bounded lock timeout and a small bounded whole-transaction retry only for PostgreSQL deadlock/serialization failures, before any external action; return a retryable conflict after exhaustion. Never retry payment captures, notifications or other irreversible external work blindly.

### Gateway reservation and idempotency

Under the order lock, persist an origin-bound payment reservation before releasing the transaction for network work. A `CREATED` intent with `externalId = null` is still a reservation, not permission for an unrelated payment or edit. A provider `SUCCEEDED` intent whose local settlement is pending likewise reserves its amount until the same provider-linked settlement commits or an explicit reconciliation resolves it. Store provider identity and unique provider transaction/link reference with the reservation. Use guarded compare-and-set state transitions, reject conflicting edits and over-reservation, and make callbacks idempotently settle the corresponding reserved order. Preserve the existing cashier override only as a permission-checked, durable and transactionally audited decision linked to the exact reservation and order. An ambiguous provider result or late callback after an override must enter reconciliation with its original provider reference and any subsequent payment; never silently discard or duplicate a confirmed capture, and never let an override cancel, overwrite or bypass a confirmed capture. Provider failures, ambiguous timeouts and captured-but-unsettled payments enter reconciliation; do not assume a timeout means no charge, release a reservation automatically, or perform network calls under database locks. These lifecycle fields/constraints need an additive migration and compatibility/rollback review before implementation.

Scope each caller-provided idempotency key by restaurant, branch, order and authenticated origin or verified provider identity. Canonicalize all original client-supplied inputs that can change the outcome or side effects: customer, coupon, loyalty request, manual discount, gift card, tip, `allowPartial`, QR override, receipt destination and consent, currency, each tender's method, amount, tendered amount and reference, and provider linkage. Include a caller-supplied immutable bill version only when supplied; never substitute a freshly computed bill version or mutable server-derived state into the fingerprint. Persist a digest of the canonical input without logging sensitive values. An identical key plus fingerprint returns the previously committed outcome; a different fingerprint or origin returns conflict without side effects. After authorization and scoping, look up the stored key, fingerprint and outcome before re-reading or recomputing the current bill, so retrying a partial payment after a later payment returns the original result instead of producing a false conflict. If no committed result exists, acquire the order lock, recheck the key under that lock, then calculate current state for the new operation. Persist an outcome even for zero-payment/zero-total checkout: the existing checkout schema and settlement allow it, and no payment row might carry the key. Catch `P2002` only for the named idempotency unique constraint, reload the persisted result under the scoped boundary, and rethrow unrelated unique failures. Define a conservative compatibility path for existing keyless requests and legacy rows: retain existing response behavior without inventing an idempotency guarantee, never equate missing fingerprints to matching payloads, and use provider reconciliation for already-captured money. Database constraints and a duplicate-data preflight must precede enforcement; exact field names and migration details require review against the current schema. Loyalty points over-debit issue #394 remains separately blocked by automated security review: do not claim this locking work corrects its points-to-discount calculation.

## Migration, permissions and rollout

Use an additive, backward-compatible migration for persisted reservation, origin-bound fingerprint/outcome and required unique constraints after duplicate-data preflight; back up first and document rollback without rewriting fiscal history. Preserve data-driven permission checks, including checkout's existing `@Auth('bills.print')`, its `RequiredBranchIdPipe` and branch-access boundary; locking is not authorization. Server-only gateway settlement and public QR entry use different trust boundaries and must be enumerated and tested separately, never made equivalent to a staff session. Introduce a database-backed writer-version fence checked in the same transaction by every writer and entry path, including callbacks, sync, offline and cleanup. Drain or upgrade all old processes and queued consumers before enforcing the fence; refuse enablement if an old writer can bypass it. Define safe handling for already-queued gateway callbacks before activation. Keep billing available for live shifts and communicate conflicts as retryable without charging twice. Security review must approve the completed writer inventory, gateway interactions, tenant scoping, timeout, fence and deadlock graph before enablement.

## Test plan and PR boundaries

Use disposable PostgreSQL integration tests with explicit two-connection barriers, not sleeps: observe the second backend actually blocked on the database lock, release the first, and exercise both serial orders before asserting committed state. Cover distinct partial payments that exceed balance together; replay the same partial payment after a later payment and assert the original persisted response, not a recomputed result; reject reuse with changed customer, coupon, loyalty, discount, gift card, tip, `allowPartial`, QR override, receipt destination/consent, tendered amount or reference; cover origin mismatch, supplied versus absent immutable bill version, zero-total and keyless/legacy outcomes, and unrelated `P2002`. Exercise partial versus full, payment versus item add/change/remove, cancellation and merge, table close with sibling recount, KOT inverse-order, offline price application, raw sync upsert, cleanup and reward writers, QR and gateway races, and opposite-direction merges. Test `CREATED` with null external ID, provider `SUCCEEDED` pending local settlement, permission-checked durable/audited cashier override, duplicate/late callbacks after override, ambiguous timeout and reconciliation without duplicate charge or loss of a confirmed capture. Check no duplicate stock/coupon/gift-card/loyalty/fiscal effects, tenant mismatch, rollback on injected failures, bounded lock wait/deadlock recovery, mixed-version fence/drain and normal single-request behavior. Unit-test transaction-aware calculations and existing API behavior; add critical API/browser coverage without weakening existing tests.

Split reviewable changes without exposing an incomplete protection as a fix: (1) failing deterministic race harness plus writer/lock inventory, no behavior claim; (2) transaction-aware calculation/refactoring with behavioral parity and tests; (3) the coordinated order-lock protocol across every participating writer, gateway and merge, with race tests and security review. If (3) cannot fit a small PR, use a default-off internal rollout mechanism only if it can be enabled atomically across all writers and cannot silently leave mixed protection; otherwise accept a larger reviewed atomic change. Gate every PR normally and run upgrade and concurrency tests before rollout.
