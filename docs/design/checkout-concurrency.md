# Checkout and bill mutation concurrency (#391)

Status: design for security review; no implementation approved. Applies to the current Nventra schema and existing API contracts, not a direct upstream port.

## Problem and invariants

`orders.service.ts` reads the order, payments and calculated bill before the checkout transaction. A partial payment leaves the order OPEN. `addItems`, item edits, header edits, cancellation and merge also check state before their write transactions. Concurrent requests can therefore act on stale payments or items. The existing final OPEN-to-PAID conditional update and transactional inventory deduction protect the losing full checkout, but do not serialize all partial payments and edits.

For each branch-scoped order, commit a serial history: no payment exceeds the freshly computed balance; after the first payment bill figures and items cannot change; paid/cancelled orders cannot be edited or paid again; duplicate request IDs do not debit or create side effects twice. A committed payment, stock movements, coupon, loyalty, gift-card and fiscal-ledger effects must agree. Rollback of a losing transaction leaves none of its side effects. Preserve the current policy for gateway settlement where money has already moved; never silently discard or duplicate it.

## Proposed transactional boundary

Use a parameterised PostgreSQL `SELECT ... FOR UPDATE` on the order row inside the Prisma interactive transaction, scoped by both order ID and the already-authorised branch ID. Return the existing not-found behavior for missing/cross-branch rows. Acquire before every read that decides a write, then reload order, items, payments, customer attachment, status and acceptance through that same transaction client. Recompute totals, locked figures, paid amount, balance, coupon eligibility, discount ceiling and loyalty inputs from the locked state. Pass the transaction client through bill and marketing helpers rather than reading stale data through the root Prisma client. Keep read-only previews advisory; checkout must independently recalculate under lock.

Make checkout, add/change/remove item, editable header/table changes, cancellation and merge participate in the same protocol. Inventory/KOT/online QR and gateway code can mutate or settle orders outside these entry points; trace every writer and ensure it calls the same transaction boundary or participates in a documented compatible lock. Do not ship a checkout-only lock while a concurrent writer can still bypass it. For merge, lock both branch-scoped order rows in deterministic ascending ID order, reload both and reject if either changed status or has payments. Define a consistent global order for order, table, customer, coupon, gift-card, stock and fiscal-ledger locks after auditing all existing paths; existing implicit database locks may make a naive order unsafe. Handle timeout/deadlock/serialization failures as a bounded retry or explicit conflict, with no automatic replay of irreversible external actions. No network, SMTP, printer or payment gateway call should run while a database transaction is held. Emit events only after commit.

Recheck `requestId` under the order lock and preserve the database uniqueness constraint. Same ID with the same request returns the committed outcome without side effects; define and test behavior when the same ID carries different payment inputs, including the existing P2002 fallback. Different IDs must each see the updated balance. Keep first-payment coupon redemption and loyalty debit atomic, avoid a second redemption on later parts, and preserve guarded cross-order customer/gift-card balances. Validate QR override against the current locked state and coordinate already-captured gateway money with its idempotent settlement path; review lock ordering with gateway/QR service before rollout.

## Migration, permissions and rollout

Prefer no schema migration: use existing order rows and payment request uniqueness. Any new request fingerprint or constraint requires an additive, backward-compatible migration with duplicate-data preflight, backup and rollback plan; do not rewrite fiscal history. Preserve permission checks as data-driven grants and branch access at controller/service boundaries; locking is not authorization. Deploy all participating writers together or use a compatible rollout barrier: mixed old/new instances can bypass a new application-level lock. Keep billing available for live shifts and communicate conflicts as retryable without charging twice. Security review must approve writer inventory, gateway interactions, tenant scoping, transaction timeout and the deadlock graph.

## Test plan and PR boundaries

Use disposable PostgreSQL integration tests with explicit two-connection barriers, not sleeps: force both requests to the relevant precondition, release them in controlled orders and assert committed database state. Cover distinct partial payments that exceed balance together, identical request replay and payload mismatch, partial versus full, payment versus item add/change/remove, cancellation and merge, QR and gateway races, and opposite-direction merges. Check no duplicate stock/coupon/gift-card/loyalty/fiscal effects, tenant mismatch, rollback on injected failures, bounded lock wait/deadlock recovery and normal existing single-request behavior. Unit-test transaction-aware calculations and existing API behavior; add critical API/browser coverage without weakening existing tests.

Split reviewable changes without exposing an incomplete protection as a fix: (1) failing deterministic race harness plus writer/lock inventory, no behavior claim; (2) transaction-aware calculation/refactoring with behavioral parity and tests; (3) the coordinated order-lock protocol across every participating writer, gateway and merge, with race tests and security review. If (3) cannot fit a small PR, use a default-off internal rollout mechanism only if it can be enabled atomically across all writers and cannot silently leave mixed protection; otherwise accept a larger reviewed atomic change. Gate every PR normally and run upgrade and concurrency tests before rollout.
